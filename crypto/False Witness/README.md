# Synopsis

False Witness is a **Very Easy** difficulty crypto challenge built on a broken decisional oracle. The server encrypts a 256-bit AES key bit by bit into a small Diffie-Hellman-style hash `H(msg) = G^msg mod P`, but lets the connecting player supply `G` themselves before anything else happens. Because `G` is never validated, a player can hand the server a generator of a small, fully enumerable subgroup instead of a proper large-order one. From there, every oracle answer can be checked against that subgroup by brute force, which leaks every key bit outright and lets the player recover the AES key that protects the flag.

# Description

Caldrin Vowmark knows that not every seal deserves belief. Some marks still carry the weight of a living vow; others only imitate one well enough to pass a glance. She can question the realm's witnesses as many times as she likes, but certainty, it turns out, is much harder to earn than a convincing lie.

## Skills Required

- Basic modular arithmetic and discrete exponentiation.
- Reading a small Python service and spotting where trust is misplaced.
- Elementary group theory: subgroup order, Lagrange's theorem.
- Scripting an interactive TCP oracle with `pwntools`.

## Skills Learned

- Why letting a caller choose their own "generator" for a hash/commitment scheme is a serious mistake.
- Small subgroup attacks: how a generator of small order turns a decisional problem into a lookup table.
- Recognizing a broken decisional assumption (deciding subgroup membership) versus a computational one (discrete log).
- Building a full membership set once and reusing it to answer many oracle queries for free.

## Step 2: Read the protocol

```console
$ cat server.py
```

On connect, the server immediately prints an AES-ECB ciphertext (the flag, encrypted under a fresh random 256-bit key), then asks the player for one integer:

```text
Here is something for you:
<hex ciphertext>
Before we start, give me the hashing generator:
```

Whatever integer the player sends (as long as `1 < G < P`) becomes `G` in `H(msg) = pow(G, msg, P)` for the rest of the session. After that, the server builds `KEY_BITS`, the 256 bits of the AES key, and for each bit position `i` it holds a pair `(sk0, sk1)` of random exponents and their hashes `(H(sk0), H(sk1))`. A menu then lets the player query an oracle at any offset `i` as many times as they like:

```text
1. Oracle
2. Exit
> 1
Enter offset: 0
Oracle result: <integer>
```

# Reverse Engineering & Analysis

```python
def H(msg):
    return pow(G, msg, P)

class Oracle:
    def oracle(self, i):
        if i in self.appeared:
            return self.appeared[i]
        ret = secrets.randbelow(2**N) if KEY_BITS[i] == 0 else PK[i % len(PK)][secrets.randbelow(2)]
        self.appeared[i] = ret
        return ret
```

For offset `i`, the oracle returns one of two very different things depending on the secret bit `KEY_BITS[i]`:

- if the bit is `0`, a uniformly random 256-bit integer, essentially noise with no structure
- if the bit is `1`, one of `H(sk0)` or `H(sk1)`, i.e. `G` raised to some exponent, an actual element of the cyclic group generated by `G`

This is a **decisional** problem by design: distinguish "real hash output" from "random noise" without knowing `sk0`/`sk1`. If `G` generates a group as large as `P` itself, that's infeasible; the two cases are computationally indistinguishable. But `G` is never checked. `P` is a fixed, public 256-bit prime, and its order `P - 1` factors into a prime `h = 65539` times a large cofactor. If a player supplies a `G` whose order is exactly `h` instead of the full group, every possible hash output lives in a set of only `h` ≈ 2<sup>16</sup> elements, small enough to enumerate completely offline in a fraction of a second.

Once that set is built, membership testing turns the decisional problem into a single hash-table lookup: a real hash output is always in the set, and a uniformly random 256-bit integer is astronomically unlikely to land in a 65539-element subset of a 256-bit field. Each oracle call at offset `i` leaks `KEY_BITS[i]` exactly, and there's no rate limit stopping a player from calling it 256 times.

A quick REPL check confirms the subgroup exists and is small enough to brute force:

```python
>>> P = 0xCD4A96D3B7FA7251A1BB765933FB676FCAE8C9026682E34F779122DFD66915BB
>>> h = 65539
>>> (P - 1) % h
0
```

`h` divides `P - 1` cleanly, so an element of order exactly `h` exists. The shipped `htb/solver.py` finds one with SageMath's `GF(P).multiplicative_generator()`, but that step doesn't actually need Sage: since `h` is prime, picking any random `r` and computing `G = pow(r, (P - 1) // h, P)` gives an element of order `h` (or, on the rare unlucky draw, `1`, easy to detect and retry) using nothing but plain Python `pow()`.

# Solution

## Exploitation Chain Overview

```
1. Factor out a small prime h from P - 1 (h = 65539 here, given in the public P).
2. Pick any r in [2, P-1) and set G = r^((P-1)/h) mod P.
   G now generates a subgroup of order h instead of the full field.
3. Read the printed AES-ECB(flag) ciphertext.
4. Send G as "the hashing generator".
5. Precompute cands = { G^i mod P : i in [0, h) }   (all h possible real hash outputs)
6. For i in 0..255:
     query the oracle at offset i
     bit_i = 1 if result in cands else 0
7. KEY = bits assembled into a 256-bit integer -> 32 bytes
8. AES-ECB-decrypt the ciphertext from step 3 with KEY -> flag
```

## Stage 1 — Forcing a small-order generator

```python
P = 0xCD4A96D3B7FA7251A1BB765933FB676FCAE8C9026682E34F779122DFD66915BB
h = 65539

while True:
    r = random.randrange(2, P - 1)
    G = pow(r, (P - 1) // h, P)
    if G != 1:
        break

assert pow(G, h, P) == 1
```

Any nontrivial `r^((P-1)/h) mod P` is an element whose order divides `h`. Since `h` is prime, that order is exactly `h` unless the result is `1`, which a single retry avoids. This `G` is what gets sent back as "the hashing generator" the server never validates.

## Stage 2 — Enumerating the whole subgroup

```python
cands = set(pow(G, i, P) for i in range(h))
```

`h` = 65539 is small enough that this set builds in well under a second and fits easily in memory. It contains every value `H(msg)` can ever produce for this session, regardless of `msg`.

## Stage 3 — Walking the oracle

```python
KEY = ''
for i in range(256):
    io.sendlineafter(b"> ", b"1")
    io.sendlineafter(b": ", str(i).encode())
    io.recvuntil(b"result: ")
    res = eval(io.recvline().strip().decode())
    KEY += str(int(res in cands))
```

For each of the 256 key bits, one oracle query and one set-membership check is all it takes. There's no budget to manage and no ambiguity: a value either sits inside the 65539-element subgroup or it doesn't.

## Stage 4 — Recovering the key and the flag

```python
KEY_bytes = int(KEY, 2).to_bytes(32)
flag = AES.new(KEY_bytes, AES.MODE_ECB).decrypt(encflag)
```

### Comments

- **The real bug is trust, not math.** `H(msg) = G^msg mod P` is a perfectly ordinary modular exponentiation. The break has nothing to do with weak arithmetic; it's that the server treats a player-supplied integer as if it were a trusted system parameter.
- **A decisional assumption only holds in a big group.** Distinguishing "hash output" from "random" is exactly as hard as the underlying group is large. Shrinking the group to 65539 elements collapses that assumption to a lookup table.
- **No rate limit, no cost.** The oracle can be called any number of times per session, so leaking all 256 bits costs nothing beyond the round trips themselves.
- **Sage isn't required.** The official solver reaches for `GF(P).multiplicative_generator()`, but since `h` is prime and known, finding an order-`h` element is a two-line loop in plain Python.
